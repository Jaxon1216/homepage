本文适合有前端基础、尚未系统学习 SQL 和 MySQL 的读者。不要求提前掌握数据库或树结构。

一个查询请求通常经过前端、后端，再到数据库。本文聚焦**后端把 SQL 交给 MySQL 之后发生的事情**：谁处理这条语句、语句怎样形成结果、底层怎样找到所需记录。

系列共三篇：第一篇讲查询、数据页与索引结构；第二篇讲联合索引、执行计划和查询优化；第三篇讲事务、并发与日志。本文以 **MySQL 8.4、InnoDB 存储引擎**为基线。

# 一、查询进入 MySQL，谁负责什么

先把 MySQL 看成协作的两部分：**Server 层理解和执行 SQL，存储引擎负责具体的数据组织与访问。**

![查询经过前端和后端进入 MySQL：Server 层负责连接、解析、优化和执行，InnoDB 负责底层的页与索引访问](/images/mysql/00-query-architecture.svg)

前端向后端发送 HTTP 请求；后端通过数据库驱动取得连接，向 MySQL 发送 SQL。MySQL 返回查询结果后，后端再组织接口响应。

SQL 是表达数据库操作要求的语言。比如下面这条语句要求取得编号为 6 的订单：

```sql
SELECT id, user_id, amount, status -- 3. 最终展示这四列
FROM orders                       -- 1. 从订单表取数据
WHERE id = 6;                     -- 2. 只保留编号为 6 的订单
```

先读懂它的要求就够了：从 `orders` 表中，找出 `id` 等于 6 的记录，返回编号、用户编号、金额和状态。第二章会集中讲这些语法的作用。

## 从收到 SQL 到返回结果

在宏观上，一条查询经过以下过程：

| 阶段 | 负责什么 | 对这条查询意味着什么 |
| --- | --- | --- |
| 连接与认证 | 建立会话、验证身份 | 后端取得可用的 MySQL 连接；连接池可以复用连接 |
| 解析与准备 | 分析语法、解析表和列等名称 | 理解 SELECT 的结构，确认 `orders`、`id` 等对象 |
| 优化 | 根据统计信息和成本选择执行计划 | 决定怎样访问订单，例如考虑主键索引 |
| 执行 | 按计划处理查询，调用引擎接口 | 向 InnoDB 请求记录，完成查询所需的处理 |
| 返回结果 | 将结果交给客户端 | 数据库驱动收到记录，后端继续处理响应 |

图和表概括的是职责，省略了权限检查、锁和清理等细节。连接可以复用，不代表每条 SQL 都重新建立一次连接。

**优化器决定采用什么执行方案，执行器按照方案执行。** SQL 写的是所需结果，通常不要求我们自己指定逐页查找的步骤。

如果旧教程在解析前画了“查询缓存”，需要注意：MySQL 8.0 已移除旧的查询缓存。后面会介绍的 InnoDB Buffer Pool 缓存的是页，与缓存整条 SQL 的结果不是一回事。[查询缓存的版本说明](https://dev.mysql.com/doc/refman/8.0/en/query-cache.html)

以 MySQL 8.4 的普通查询为例，主要经过以下阶段：

1. **连接与认证**：建立会话、验证身份，取得权限相关信息；连接池可以复用已有连接。
2. **解析**：进行词法、语法分析，生成语句的内部表示。
3. **预处理与名称解析**：解析表和列，检查对象与语义；本文架构图把这一步归入“解析与准备”。
4. **优化**：根据统计信息和成本模型选择访问路径、索引及连接顺序，生成执行计划。
5. **执行与返回**：执行器按计划调用存储引擎接口，处理过滤、连接、聚合或排序，并向客户端返回结果。

这是职责划分的概括，权限检查等工作会出现在相关阶段。MySQL 8.0 已移除旧查询缓存，现代执行链路不应再把它作为必经环节。

</details>

<details>
<summary>MySQL Server 层与存储引擎分别负责什么？</summary>

**Server 层负责通用的 SQL 处理，存储引擎负责数据的具体组织与访问。**

- Server 层处理连接、认证、语句解析、优化和执行；执行器通过引擎接口请求记录。
- 存储引擎实现记录、页、索引的组织与读写，以及相应的事务、锁和恢复能力。不同引擎支持的能力不同。
- 存储引擎可以按表选择；同一条 SQL 可以由 Server 层统一处理，再访问使用不同引擎的表。

</details>

# 二、SQL 怎样表达查询要求

用 [SQL 50](https://leetcode.cn/studyplan/sql-free-50/) 中的 [第 1581 题：进店却未进行过交易的顾客](https://leetcode.cn/problems/customer-who-visited-but-did-not-make-any-transactions/)：**返回顾客编号，以及该顾客到店但没有交易的次数。** 以下使用缩小后的自编数据。

## 输入：两张表

`Visits` 每行是一次到店记录：

| visit_id | customer_id |
| --- | --- |
| 1 | 10 |
| 2 | 20 |
| 3 | 20 |
| 4 | 30 |

`Transactions` 每行是一笔交易，`transaction_id` 是唯一且非空的交易编号，通过 `visit_id` 对应到店记录：

| transaction_id | visit_id | amount |
| --- | --- | --- |
| 101 | 1 | 50 |

## SQL 与输出

注释中的数字是**逻辑处理顺序**，用于理解结果；不表示 MySQL 必须按这个顺序执行物理操作。

```sql
-- 5. SELECT：最终只展示 customer_id、count_no_trans 两列；AS 指定结果列名
SELECT v.customer_id, COUNT(*) AS count_no_trans
-- 1. FROM：从到店记录表取数据，v 是 Visits 的别名
FROM Visits AS v
-- 2. LEFT JOIN / ON：按 visit_id 匹配交易，没匹配上的到店记录也保留，右侧列补 NULL
LEFT JOIN Transactions AS t ON t.visit_id = v.visit_id
-- 3. WHERE：只保留没有匹配交易的到店记录
WHERE t.transaction_id IS NULL
-- 4. GROUP BY：按顾客分组；COUNT(*) 统计每组的到店记录数
GROUP BY v.customer_id;
```

输出（原题允许任意顺序）：

| customer_id | count_no_trans |
| --- | --- |
| 20 | 2 |
| 30 | 1 |

**SELECT 写了什么列或表达式，结果就展示什么列。** 这里不会展示 `visit_id`、`transaction_id` 或 `amount`，也不会改变原表的列。

## HAVING、ORDER BY、LIMIT 的作用

下面是补充写法，增加了原题没有要求的筛选、排序和截取：

```sql
-- 6. SELECT：最终仍只展示 customer_id、count_no_trans 两列
SELECT v.customer_id, COUNT(*) AS count_no_trans
-- 1. FROM：取到店记录
FROM Visits AS v
-- 2. LEFT JOIN / ON：匹配交易，未匹配时右侧列补 NULL
LEFT JOIN Transactions AS t ON t.visit_id = v.visit_id
-- 3. WHERE：只保留没有交易的到店记录
WHERE t.transaction_id IS NULL
-- 4. GROUP BY：按顾客分组，并计算各组的 COUNT(*)
GROUP BY v.customer_id
-- 5. HAVING：只保留次数至少为 2 的组
HAVING COUNT(*) >= 2
-- 7. ORDER BY：按次数降序；次数相同时按顾客编号升序
ORDER BY count_no_trans DESC, v.customer_id ASC
-- 8. LIMIT：只返回排在第一位的一行
LIMIT 1;
```

输出：

| customer_id | count_no_trans |
| --- | --- |
| 20 | 2 |

`DESC` 是降序，`ASC` 是升序。MySQL 的 `ORDER BY`、`GROUP BY`、`HAVING` 可以引用 SELECT 别名，同层 WHERE 不能直接引用它。[别名规则](https://dev.mysql.com/doc/refman/8.4/en/problems-with-alias.html)

<details>
<summary>SELECT 查询的逻辑处理顺序是什么？</summary>

常见的逻辑顺序是：

`FROM / JOIN ... ON → WHERE → GROUP BY 与聚合 → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET`。

它描述结果的形成语义，SQL 的书写顺序仍然以 SELECT 开头；优化器可以做等价的连接重排、条件下推等变换，物理执行不必逐步照搬这个顺序。

本文代码的编号只计算该语句实际使用的子句，并把分组和聚合合并计为一步。MySQL 允许 `GROUP BY`、`HAVING`、`ORDER BY` 使用 SELECT 别名，同层 WHERE 不能直接使用这些别名。

</details>

<details>
<summary>WHERE 和 HAVING 有什么区别？</summary>

**WHERE 在分组聚合前筛选行，HAVING 在分组聚合后筛选组或聚合结果。**

- WHERE 决定哪些输入行参与后续计算，不能直接使用同层的聚合结果，例如 `COUNT(*) >= 2`。
- HAVING 可以使用 `COUNT()`、`SUM()` 等聚合值，例如筛选订单数至少为 2 的用户。
- HAVING 不要求一定写出 GROUP BY；不带 GROUP BY 的聚合查询，也可以对整体聚合结果进行筛选。

能在聚合前确定的行条件，应写清为 WHERE；依赖聚合值的条件放在 HAVING。

</details>

<details>
<summary>INNER JOIN 与 LEFT JOIN 有什么区别？ON 与 WHERE 呢？</summary>

- **INNER JOIN**：只返回满足连接条件的匹配行。
- **LEFT JOIN**：保留左表的行；没有右表匹配时，右表列补 NULL。
- **ON**：定义连接阶段的匹配条件。
- **WHERE**：继续筛选连接结果；在逻辑上也会检查外连接补出的 NULL 行。

因此，LEFT JOIN 中把右表条件从 ON 移到 WHERE，可能过滤掉未匹配的左表行。例如 `WHERE t.amount > 0` 不能让补出的 NULL 行通过；`WHERE t.transaction_id IS NULL` 则可用于保留未匹配行，前提是用于判断的右表列在真实匹配记录中不为 NULL。本文的 `transaction_id` 是唯一且非空的交易编号。

不是所有条件移动都会改变结果，必须结合连接类型和 NULL 语义判断。[JOIN 规则](https://dev.mysql.com/doc/refman/8.4/en/join.html)

</details>

<details>
<summary>COUNT(*)、COUNT(1)、COUNT(列) 有什么区别？</summary>

- `COUNT(*)` 统计查询结果中的行数，行中包含 NULL 也计数。
- `COUNT(1)` 统计常量 1 的非 NULL 个数，所以同样是在数行。InnoDB 对它与 `COUNT(*)` 采用相同处理，没有固定的性能优势。
- `COUNT(列)` 只统计该列不为 NULL 的行，因此结果可能小于前两者。

本题过滤后 `t.transaction_id` 全是 NULL，所以 `COUNT(t.transaction_id)` 为 0，应使用 `COUNT(*)` 统计未交易的到店记录。

InnoDB 不维护对所有事务都通用的精确总行数；无条件 `COUNT(*)` 仍需要统计当前事务可见的索引记录，不能回答成固定的 O(1)。[COUNT 的定义与 InnoDB 行数统计](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)

</details>

建表用 `CREATE TABLE`，加行用 `INSERT`，改行用 `UPDATE`，删行用 `DELETE`；本文的查询使用 `SELECT`。

# 三、存储引擎把记录放在哪里

InnoDB 通常把一张表的数据组织在主键 B+ 树中。先看整体：根页和中间页负责指路，叶子页保存行记录，叶子页之间按主键顺序连接。

![三级主键 B+ 树总览：黄色主键、白色子页引用、绿色行数据；根页和中间页导航，叶子页保存订单四个字段](/images/mysql/01-storage-tree-overview.svg)

图中每个节点对应一个页；黄色格是键值，白色格引用下一层的页，叶子页里的绿色格是行的其他字段。这里只展开订单 1～8，其余子树省略。真实的这八条短记录通常能放在一个叶子页中，三级布局用于说明结构。

下面回到第一章的订单查询，后文的配图沿用这张 `orders` 表：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 1 | 1 | 120.00 | paid |
| 2 | 1 | 80.00 | paid |
| 3 | 2 | 160.00 | paid |
| 4 | 2 | 90.00 | paid |
| 5 | 3 | 60.00 | paid |
| 6 | 3 | 70.00 | paid |
| 7 | 4 | 300.00 | paid |
| 8 | 3 | 900.00 | unpaid |

`id` 是订单主键，唯一标识一行，不能重复或为 NULL；`user_id` 是用户编号，`amount` 是金额，`paid` / `unpaid` 分别表示已支付 / 未支付。

本文使用 InnoDB。它负责索引与记录的存储和访问，也提供事务、锁与崩溃恢复等能力；后几项会在第三篇展开。先只看读取一条订单所涉及的结构。

## 为什么本文使用 InnoDB

存储引擎可以按表选择。MySQL 8.4 默认使用 InnoDB；常见面试会把它与 MyISAM 比较：

| 能力 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务提交与回滚 | 支持 | 不支持 |
| 写入时的锁粒度 | 支持行级锁，也有表级锁 | 主要是表级锁 |
| 外键约束 | 支持 | 不支持 |
| 表数据组织 | 由聚簇索引组织 | 数据与索引文件分离 |

InnoDB 还提供事务崩溃恢复能力。事务、行锁和恢复机制会在第三篇展开；本篇先理解它怎样组织数据。[InnoDB 能力](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) · [MyISAM 能力](https://dev.mysql.com/doc/refman/8.4/en/myisam-storage-engine.html)

## 从表和行，进入数据页

InnoDB 把索引记录组织在一个个**页**中。一页可以容纳多条记录，还包含页头、页目录等管理信息。

![orders 表在逻辑上是行和列，在 InnoDB 中以页组织：一页包含多条记录与管理信息](/images/mysql/01-table-page.svg)

普通 InnoDB 索引页的默认大小是 **16 KiB，也就是 16384 字节**。页大小由实例初始化时的配置决定，不是所有 MySQL 环境都只能使用这个大小。[InnoDB 索引的物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

一页能放多少行，取决于记录大小、管理信息以及页的利用情况。同样大小的一页，存短订单记录和存很长的文本，能容纳的数量不同。

所以查找一条记录，需要解决两个问题：先找到它所在的页，再找到页里的那条记录。第四章先看页内查找，第五章再把视角扩到很多页。

## Buffer Pool：页可能已经在内存里

InnoDB 会把数据页、索引页缓存在 **Buffer Pool**（缓冲池）中。读取所需页时，先看它是否已经在缓冲池里；如果已经在，就能在内存中访问，否则需要把页读入。[Buffer Pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

这与第一章提到的旧查询缓存不同：

| 对象 | 缓存什么 | 对查询的影响 |
| --- | --- | --- |
| 旧查询缓存 | 特定查询的结果 | MySQL 8.0 已移除 |
| InnoDB Buffer Pool | 数据页、索引页等 | 不同查询可能复用已经读入内存的页 |

<details>
<summary>InnoDB 和 MyISAM 有什么区别？为什么通常使用 InnoDB？</summary>

可以从事务与可靠性、并发能力、存储组织三个方面回答：

1. **事务与可靠性**：InnoDB 支持事务提交、回滚和崩溃恢复，也支持外键；MyISAM 不支持事务和外键，不能提供同等的事务崩溃恢复能力。
2. **并发能力**：InnoDB 支持行级锁和 MVCC；MyISAM 主要使用表级锁，不支持 MVCC。InnoDB 也有表级锁，不能把它描述成“只有行锁”。
3. **存储组织**：InnoDB 用聚簇索引组织行数据，二级索引携带聚簇键；MyISAM 的数据文件与索引文件分离，索引记录引用数据记录的位置。

InnoDB 是 MySQL 8.4 的默认引擎，通常更适合需要并发写入和可靠性的通用业务，不能笼统地说“MyISAM 查询总是更快”。[InnoDB 能力](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) · [MyISAM 能力](https://dev.mysql.com/doc/refman/8.4/en/myisam-storage-engine.html)

</details>

<details>
<summary>Buffer Pool 的作用是什么？三层 B+ 树就有三次磁盘 I/O 吗？</summary>

**Buffer Pool 是 InnoDB 缓存数据页和索引页的内存区域，用来减少物理 I/O。**

需要访问一个页时，若命中缓冲池，就直接读取内存；未命中才需要把页读入。旧查询缓存缓存的是 SQL 结果，两者不是同一种缓存。

三层树的单条定位路径通常经过三层页，但不能直接等同于三次磁盘读取。实际 I/O 还取决于缓存命中；范围查询、回表等也可能继续访问其他页。[Buffer Pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

</details>

# 四、找到一个页，怎样找到其中的记录

先看主键索引中保存行记录的页，这种页叫作**叶子页**；下一章会解释它在整棵树中的位置。页中的记录通过“下一条记录”的信息，按主键顺序串成记录链。

图中的订单编号沿用 1～8。这里关注记录之间的引用关系，方块的摆放位置不代表它们在页内的实际字节地址。

![数据页中的页目录、记录分组与记录链：目录槽指向组末记录，各记录用下一条记录的信息按主键串联](/images/mysql/02-page-directory.svg)

图中既画出了用户记录，也画出了两条边界记录。分组用来说明页内查找，SQL 示例不能直接验证真实页里恰好形成了相同的分组。

## 先读懂图里的字段和连线

| 图中元素 | 含义 |
| --- | --- |
| 左侧的目录槽 | 保存指向页内某条记录的位置，作为查找分组的入口 |
| 红色虚线 | 目录槽指向其负责的记录组的最后一条记录 |
| 黑色连线 | 一条记录指向下一条记录，按主键顺序串联 |
| `n_owned` | 本记录作为组末记录时，负责的组内记录数 |
| 主键、行数据 | 订单编号以及该订单的字段内容 |
| infimum／supremum | 表示页内最小、最大边界的系统记录，不是用户插入的订单 |

普通组通常包含 4～8 条记录，首尾组有例外。图中普通组分别是订单 1～4 和 5～8：组末记录 4、8 的 `n_owned` 为 4，其余普通记录为 0；0 不代表没有数据，而是这条记录不负责一个目录组。[页目录定义与分组常量](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/include/page0page.h)

这套“目录槽指向分组边界”的结构，就是**页目录（Page Directory）**。它不需要为每一条记录都建立一个槽。

## 查询 id = 6 时，怎样利用目录

如果只顺着记录链从头找，需要经过 1、2、3、4、5、6。页目录可以先缩小范围：

1. 对目录槽做二分查找，通过槽指向的记录比较主键，确定 `4 < 6 <= 8`。
2. 确认目标应在“记录 4 之后、记录 8 以内”的那组。
3. 从前一组末尾记录 4 的下一条开始，沿链比较 5、6，找到订单。

这里要同时看清两种连线：**目录槽指向组末，实际的组内查找从前一个边界向后走。** 不能把图理解成“到记录 8 以后再倒着找 6”。[页内查找实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/page/page0cur.cc)

图上的黑链表示逻辑顺序。它不要求这些记录按物理地址紧挨着排列，也不意味着每一步都要重新读取磁盘：此时我们讨论的已经是一个页内部的查找。

**面试串联**

<details>
<summary>定位到 B+ 树叶子页后，InnoDB 如何查找具体记录？</summary>

**通过页目录缩小范围，再沿页内记录链完成查找。**

1. 页内记录按索引键的逻辑顺序连接，并被划分为若干组；页目录中的槽指向各组的末尾记录。
2. 对目录槽做二分查找，通过槽指向的记录比较键值，确定目标所在的组。
3. 从前一组的末尾记录向后，沿记录链做少量比较，找到目标记录，或确认记录不存在。

页目录没有为每条记录建立一个槽；也不是找到组末后再倒着遍历。`n_owned` 是组末记录负责的记录数，其他普通记录的 0 不表示没有数据。内部索引页也使用页目录。

</details>

# 五、页越来越多，怎样找到目标页

上一章解决了页内查找。订单不断增加后，记录需要放进更多页，数据库还要知道该访问哪个页。

索引就是为查找数据维护的检索结构。这里的普通 InnoDB 索引用 B+ 树组织，借助有序的键值缩小扫描范围。主键索引同时组织表数据；其他字段也可以单独建立索引。

可以给这些页再建立一层目录：在上层保存**导航键和子页信息**，根据查询值选择下一层的页。

## 从一层目录，到一棵 B+ 树

![订单主键 B+ 树：上层按范围指向三个叶子页，查询 id 为 6 时访问中间页，叶子页按键值顺序连接](/images/mysql/03-primary-btree.svg)

图中把订单分到三个教学页：1～3、4～6、7～8。上层导航键用 1、4、7 表示范围下界，查询 6 时进入中间页，再用页内结构找到记录。

先认识这几个名称：

| 名称 | 在图中负责什么 |
| --- | --- |
| 根节点 | 查找入口，也对应一个页 |
| 非叶子节点，也叫内部节点 | 存放导航键和子页信息，帮助选择下一层 |
| 叶子节点 | 没有子页；主键索引的叶子记录承载行数据 |
| 树高 | 从根走到叶子经过的层数，本图是两层 |

当一层导航页放不下所有子页信息，还可以增加中间层。这样就形成了**多个分支、叶子位于同一深度的 B+ 树**。节点对应页，而不是一条订单记录。

图为了展示分支，把八条记录画进了三个叶子页；真实的这些短记录通常可以放在同一叶子页中，根也就可以同时是叶子。图中的导航键省略了最左项的特殊最小标记，实际父层导航键也不必始终等于子页当前最小记录。

## 为什么使用 B+ 树

考虑的是按页存储与访问的成本：一个内部页可以容纳很多导航项，一次访问就能比较多个分支，用相对较少的层数覆盖大量记录。

| 结构 | 特点 | 与这个查询场景的关系 |
| --- | --- | --- |
| 二叉搜索树 | 每个节点至多两个子节点 | 大量数据下，相比高分支数的树，导航层数可能更多；普通二叉树还可能退化 |
| B 树 | 内部节点也可以保存用户记录 | 在相似页大小和键大小下，较大的用户记录会占用内部页空间 |
| B+ 树 | 内部节点主要存导航信息，用户记录集中在叶子 | 内部页能容纳较多分支，叶子层也适合有序扫描 |
| 普通 Hash 索引 | 擅长等值定位，不按键值顺序组织 | 不天然支持沿键值顺序继续做范围扫描 |

这不是说每种其他结构都不能查数据，而是解释 B+ 树如何兼顾按页访问、等值查找与范围扫描。这里讨论普通有序索引，全文、空间等索引另有结构。[B-tree 与 Hash 索引的比较](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)

页目录使用二分查找，与 B+ 树有很多分支并不矛盾：**二分是比较和查找的方法，树是页与页的组织方式。**

## 三层 B+ 树能放多少行

用一组假设估算：一个内部页能指向 1000 个子页，一个叶子页能放 100 条记录。

| 树高（包含根和叶子） | 计算 | 大致容量 |
| --- | --- | --- |
| 1 层，根就是叶子 | 100 | 100 条 |
| 2 层，根 → 叶子 | 1000 × 100 | 10 万条 |
| 3 层，根 → 中间页 → 叶子 | 1000 × 1000 × 100 | 1 亿条 |

这些数是教学假设，不是 MySQL 的固定容量。实际需要按页大小、索引键和子页引用的大小、行记录大小及页利用率估算。**B+ 树的优势在于分支多，增加一层就能覆盖更多页。**

## 范围查询怎样继续往后读

例如要取得编号 5～7 的订单：

```sql
SELECT id, amount           -- 3. 最终展示编号、金额两列
FROM orders                 -- 1. 从订单表取数据
WHERE id BETWEEN 5 AND 7     -- 2. 保留编号 5～7 的订单，包含两端
ORDER BY id;                -- 4. 按编号升序排列
```

结果为：

| id | amount |
| --- | --- |
| 5 | 60.00 |
| 6 | 70.00 |
| 7 | 300.00 |

`BETWEEN` 包含两端。沿图推演，可以先从根找到记录 5 所在的中间页，读到 6 后，沿叶子页之间的链接进入下一页，继续取 7。

因此，不必为范围中的每条记录都重新从根查一遍。叶子页按键值顺序双向连接，但逻辑相邻不保证磁盘物理位置连续。[InnoDB B+ 树实现中的页链接与导航记录](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/btr/btr0btr.cc)

## 插入时页满了怎么办

新记录要按键值顺序插入目标叶子页。页有空间时可以直接放入；空间不足时，可能先整理页内空间，必要时分配新页，把记录分到不同页，并调整页间链接和父页导航项，这就是**页分裂**。

如果父页也容纳不下新的导航项，结构调整可能继续向上；根需要分裂时，树才可能增高。分裂不是简单地把一行追加到表末尾，也不是每次插入都会发生。[InnoDB B+ 树维护实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/btr/btr0btr.cc)

<details>
<summary>什么是索引？索引有哪些收益和代价？</summary>

**索引是帮助存储引擎快速定位记录的数据结构，用额外空间和写入维护换取更少的扫描。**

- **收益**：加快合适的等值、范围查询；利用有序性减少部分排序；通过唯一索引约束唯一性，通过覆盖索引减少额外取列的回表。
- **代价**：占用磁盘和 Buffer Pool 空间；插入、删除、更新相关列时需要维护索引，索引越多通常意味着更多写入工作。
- **适用条件**：是否受益取决于查询条件、数据分布、返回行数和回表成本。有索引不等于优化器一定选择它，不能笼统地说“加索引一定更快”。

</details>

<details>
<summary>为什么 InnoDB 普通索引选择 B+ 树，而不是 B 树、二叉树或哈希表？</summary>

B+ 树是一棵**多路、平衡、有序**的搜索树，适合按页访问数据：

- **相比二叉树**：一页可以保存多个导航项，分支数大，通常能用更少层数覆盖更多记录。
- **相比 B 树**：非叶子页主要保存导航键和子页引用，数据记录集中在同一层叶子页；在相似页大小和键大小下，内部页更容易容纳较多导航项。
- **相比哈希表**：保持键值顺序，适合范围查找和有序扫描；哈希结构主要适合完整键等值定位。
- **范围查询**：先定位范围起点，再沿叶子页链接继续扫描，不必逐条从根查找。

选择依据是页式存储与多种查询方式的综合成本，不代表 B+ 树在所有内存等值查询中都比哈希快。这里讨论普通有序索引，全文和空间索引另有结构。

</details>

<details>
<summary>三层 B+ 树能存多少条记录？怎样估算？</summary>

没有固定答案。应先给出页大小、键与子页引用大小、记录大小，以及页利用率的假设。

设每个内部页平均有 `f` 个分支，每个叶子页平均放 `L` 条记录，树高 `h` 包含根和叶子。在分支数近似均匀的教学模型中，容量约为 `f^(h-1) × L`。

例如本文假设 `f = 1000`、`L = 100`，三层约为 `1000 × 1000 × 100 = 1 亿` 条。真实估算需要扣除页头、记录头和页目录等开销，并考虑页利用率。这个容量估算也不能推导出固定的磁盘 I/O 次数。

</details>

<details>
<summary>插入、更新、删除数据时，索引会发生什么变化？</summary>

- **插入**：需要向聚簇索引和相关二级索引加入记录。页有空间时可以直接插入；空间不足时可能重组或分裂，并更新页链接和父层导航项。
- **更新**：索引列的键值变化时，需要维护旧索引项和新索引项；修改聚簇键还会影响相关二级索引。只更新非索引列，不需要重新排列该二级索引，但行长度变化仍可能影响聚簇记录的页内布局。
- **删除**：InnoDB 通常先做删除标记，满足清理条件后再由后台 purge 清理；不是执行 DELETE 后所有索引页立即收缩。页利用率降低后也可能发生页合并或重组。

不是每次插入都会分裂，也不是每次分裂都会增加树高；需要根部增层时，树高才会增加。[InnoDB 多版本与索引维护](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

</details>

# 六、按主键查与按其他字段查，有什么不同

前面按订单编号查询。现在换成查询用户 3 的全部订单，条件是 `user_id = 3`。

这几笔订单的主键是 5、6、8。它们并不形成只包含该用户订单的连续主键区间：中间的 7 属于用户 4。主键树按订单 id 导航，不能直接依据用户编号找到一个精确的小范围。

## 主键索引：叶子记录承载行数据

我们给 orders 显式定义了 `PRIMARY KEY (id)`。在这张 InnoDB 表中，主键索引就是**聚簇索引**：记录按主键组织，叶子记录承载行数据。

因此，最开始的查询：

```sql
SELECT id, user_id, amount, status -- 3. 最终展示这四列
FROM orders                       -- 1. 从订单表取数据
WHERE id = 6;                     -- 2. 只保留编号为 6 的订单
```

沿主键树找到记录后，就能取得：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 6 | 3 | 70.00 | paid |

“叶子记录承载行数据”是存储组织上的描述。很长的变长字段可能放到溢出页，不能理解成任何一行的所有字节都一定在同一个叶子页里。[InnoDB 行格式](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html)

如果没有显式主键，InnoDB 会选择第一个所有列均为 NOT NULL 的唯一索引作为聚簇索引；再没有，就生成隐藏行 ID。因此，没有声明主键也不意味着表中没有聚簇索引。[聚簇索引与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

## 二级索引：换一种排序组织，再带上主键

为了按用户编号查订单，这里假设 orders 已建立单列二级索引 `idx_user_id (user_id)`。

这是一棵二级索引，也叫辅助索引。它的叶子记录包含**索引列值和该行的主键值**。按用户编号观察，内容可以简化为：

| user_id | 订单主键 id |
| --- | --- |
| 1 | 1 |
| 1 | 2 |
| 2 | 3 |
| 2 | 4 |
| 3 | 5 |
| 3 | 6 |
| 3 | 8 |
| 4 | 7 |

同一用户的索引项聚到了一起。现在可以先按 user_id 定位，再得到对应订单主键。

![二级索引按 user_id 找到主键 5、6、8，再通过主键索引取得订单；展开编号 6 的一次回表](/images/mysql/04-secondary-lookup.svg)

执行下面的查询时，如果优化器选择这条二级索引路径：

```sql
SELECT id, user_id, amount, status -- 3. 最终展示这四列
FROM orders                       -- 1. 从订单表取数据
WHERE user_id = 3                  -- 2. 只保留用户 3 的订单
ORDER BY id;                      -- 4. 按编号升序排列
```

可以沿图分成两段理解：

1. 在 `idx_user_id` 中定位用户 3，取得主键 5、6、8。
2. 索引中没有 amount 和 status，需要根据这些主键访问聚簇索引，取得所需字段。

结果是：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 5 | 3 | 60.00 | paid |
| 6 | 3 | 70.00 | paid |
| 8 | 3 | 900.00 | unpaid |

这里没有筛选支付状态，所以未支付的订单 8 也在结果中。图中只展开订单 6 的一次查找，其余匹配记录也需要取得查询要求的字段。

**从二级索引取得主键后，再访问聚簇索引取数据，通常称为回表。** 二级索引携带的是主键值，不是某行固定的磁盘地址。

## 什么时候可以避免回表

如果这条查询的条件和输出只需要二级索引里已有的列：

```sql
SELECT user_id, id -- 3. 最终只展示用户编号、订单编号
FROM orders        -- 1. 从订单表取数据
WHERE user_id = 3   -- 2. 只保留用户 3 的订单
ORDER BY id;       -- 4. 按订单编号升序排列
```

| user_id | id |
| --- | --- |
| 3 | 5 |
| 3 | 6 |
| 3 | 8 |

所需字段已经由 `idx_user_id` 覆盖，可以省去为获取额外列而回表。这就是**覆盖索引**的基本含义：它描述索引与某条查询之间的关系，不是一种独立的建索引语法。

不过，“存在这棵索引”和“优化器一定选择它”是两回事。只有八条记录的小表，扫描也可能很便宜。第二篇会用执行计划和合适的数据规模讨论选择依据，本篇先把两条访问路径分清。

## 索引的代价与主键选择

多建一棵索引，会多占存储空间和 Buffer Pool 空间。插入一行时，需要维护聚簇索引和相关二级索引；修改索引列、删除记录也会带来维护工作。**查询节省的扫描，要与写入和空间成本一起考虑。**

主键选择还会影响所有二级索引：

| 主键特征 | 对存储结构的影响 |
| --- | --- |
| 短 | 二级索引携带的主键更小，同一页更容易容纳更多索引项 |
| 稳定 | 避免修改聚簇键时连带调整二级索引中的主键值 |
| 近似递增 | 新记录通常靠近主键树尾部，减少分散到不同页的随机访问 |

因此，自增整数是常见选择。随机 UUID 若以长字符串存储，既增大键值，也会把插入分散到更多页；若使用 UUID，还要考虑紧凑编码与有序程度。递增值也需要新页，并不能避免所有页分裂；高并发时还可能出现尾页热点。[主键长度与二级索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) · [顺序与随机插入的页利用率](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

<details>
<summary>InnoDB 聚簇索引和二级索引有什么区别？</summary>

区别在于**叶子记录保存什么，以及表数据怎样组织**：

- 聚簇索引的叶子记录承载行数据；一张 InnoDB 表只有一个聚簇索引，因为行数据只能按这一套聚簇键顺序组织。
- 二级索引的叶子记录保存二级索引列值和对应的聚簇键；一张表可以有多个二级索引。本文显式声明了主键，因此聚簇键就是主键。
- 二级索引保存的是键值，不是行的固定磁盘地址。需要它未包含的列时，再按聚簇键访问聚簇索引。

很长的变长字段可能使用页外存储，“叶子记录承载行数据”不意味着一行所有字节必定在同一页。

</details>

<details>
<summary>没有显式定义主键，InnoDB 如何选择聚簇索引？</summary>

选择顺序是：

1. 如果定义了 PRIMARY KEY，使用主键。
2. 否则使用**第一个所有索引列都为 NOT NULL 的 UNIQUE 索引**。
3. 如果仍不存在，生成隐藏的聚簇索引 `GEN_CLUST_INDEX`，使用内部的 6 字节行 ID。

因此，没有显式声明主键不等于没有聚簇索引。复合主键也仍然是一套聚簇键，不会因此产生多个聚簇索引。[聚簇索引选择规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

</details>

<details>
<summary>什么是回表和覆盖索引？覆盖索引一定完全不访问聚簇记录吗？</summary>

**回表**：通过二级索引取得聚簇键，再访问聚簇索引取得所需记录。

**覆盖索引**：某条查询所需的过滤、连接和返回列等，已经包含在使用的索引中，可以从该索引取得结果，省去为获取额外列而回表。覆盖与否是索引和具体查询之间的关系，不是一种独立的建索引语法；修改 SELECT 的列可能改变覆盖情况。

**边界**：字段被覆盖，不代表任何情况下都完全不访问聚簇记录。InnoDB 在二级索引记录带有删除标记，或需要检查较新修改的可见性等情况下，仍可能访问聚簇记录。这里的“避免回表”主要解释获取列的路径，多版本可见性会在第三篇展开。[InnoDB 多版本与覆盖索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

</details>

<details>
<summary>主键应该使用自增 ID 还是 UUID？</summary>

InnoDB 的主键会组织聚簇索引，并进入相关二级索引，因此通常希望它**短、稳定、唯一，并尽量保持有序**。

- **自增整数**：键值紧凑、比较简单，新记录通常靠近主键树尾部，可减少分散的随机页访问；但仍会分配新页，高并发下也可能出现尾页热点。
- **随机 UUID**：插入位置更分散；若使用较长字符串编码，还会放大聚簇索引和二级索引的体积。
- **选择条件**：需要全局唯一 ID 时，还要比较生成方式、编码长度、有序程度和业务约束；紧凑编码、近似有序的 ID 与随机长字符串不能一概而论。

不能回答成“自增永远更好”或“UUID 必然不能用”。主键变长影响所有携带它的二级索引，近似递增则主要影响记录插入位置。

</details>

## 把一条查询的路径连起来

回到 `WHERE id = 6` 这条查询：

```text
后端发送 SQL
  → Server 解析语句、确认对象、选择计划
  → 执行器调用 InnoDB
  → 沿主键 B+ 树定位叶子页
  → 在页内借助页目录和记录链找到订单 6
  → 返回所需字段，后端继续处理响应
```

这条路径中的页可能已经在 Buffer Pool 中。换成按 user_id 查找并选择二级索引时，则可能多出根据主键回表的过程。

第二章告诉我们**查询结果应该包含什么**，后四章解释了**存储引擎可以怎样找到这些记录**。像第二章这样的关联、聚合查询，还需要执行器按照计划组织相应处理；不能把复杂查询等同于一次主键查找。
