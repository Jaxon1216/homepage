本文适合有前端基础想要转型全栈、尚未系统学习 SQL 和 MySQL 的读者。

如果你有数据结构基础，尤其是链表、树、指针，会很容易理解本文。

作为前端开发者，我们肯定都知道，一个查询请求通常经过前端、后端，再到数据库。本文聚焦**后端把 SQL 交给 MySQL 之后发生的事情**：谁处理这条语句、语句怎样形成结果、底层怎样找到所需记录。

系列共三篇：第一篇讲查询、数据页与索引结构；第二篇讲联合索引、执行计划和查询优化；第三篇讲事务、并发与日志。本文以 **MySQL 8.4、InnoDB 存储引擎**为基线。

# 一、查询进入 MySQL，谁负责什么

先把 MySQL 看成协作的两部分：**Server 层理解和执行 SQL，存储引擎负责具体的数据组织与访问。**

![查询从前端、后端进入 MySQL，Server 层处理 SQL，InnoDB 访问底层数据](/images/mysql/00-query-architecture.svg)

前端向后端发送 HTTP 请求；后端通过数据库驱动取得连接，向 MySQL 发送 SQL。MySQL 返回查询结果后，后端再组织接口响应。

比如下面这条 SQL，要求取得编号为 6 的订单：

```sql
SELECT id, user_id, amount, status -- 3. 最终展示这四列
FROM orders                       -- 1. 从订单表取数据
WHERE id = 6;                     -- 2. 只保留编号为 6 的订单
```

先按注释里的顺序看，会更容易理解：`FROM` 选的是哪张表，`WHERE` 筛选哪些行，`SELECT` 决定最终展示什么列。

这里也可以重命名，使用 `AS`。比如 `amount AS total`，结果中的列名就叫 `total`，原表的列名不会因此改变。

下文会介绍更完整的语句顺序。

## 从收到 SQL 到返回结果

在宏观上，一条查询经过以下过程：

| 阶段 | 负责什么 | 对这条查询意味着什么 |
| --- | --- | --- |
| 连接与认证 | 建立会话、验证身份 | 后端取得可用的 MySQL 连接；连接池可以复用连接 |
| 解析与准备 | 分析语法、解析表和列等名称 | 理解 SELECT 的结构，确认 `orders`、`id` 等对象 |
| 优化 | 根据统计信息和成本选择执行计划 | 决定怎样访问订单，例如是否使用主键索引 |
| 执行 | 按计划处理查询，调用引擎接口 | 向 InnoDB 请求记录，完成过滤等处理 |
| 返回结果 | 将结果交给客户端 | 数据库驱动收到记录，后端继续处理响应 |

有些旧资料会在这里画一个“查询缓存”。旧查询缓存保存的是 **SQL 文本和这条 SQL 的查询结果**。同样的查询再次到来，满足缓存命中条件时，就可以直接返回之前的结果，不用重新解析、执行。

但是，只要相关表发生修改，涉及这张表的查询缓存就需要失效。经常更新的表，可能刚存好结果就要清掉，缓存本身也需要维护。MySQL 8.0 已经移除了这个功能，所以本文的执行链路里没有它。[旧查询缓存说明](https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/query-cache.html)

# 二、SQL 怎样表达查询要求

关于基础语法，我觉得先掌握常用命令、能看懂语句在做什么，就可以开始练习。一个直接的方式是刷 [LeetCode SQL 基础 50 题](https://leetcode.cn/studyplan/sql-free-50/)。

这里选 [第 1581 题：进店却未进行过交易的顾客](https://leetcode.cn/problems/customer-who-visited-but-did-not-make-any-transactions/)。原题要求：返回顾客编号，以及该顾客到店但没有交易的次数。下面用一组自编数据，再加上筛选、排序和截取，看看这些语句分别会得到什么。

## 准备：两张表

第一张表叫 `Visits`，每行是一次到店记录。看列名，第一列是到店记录的 ID，第二列是顾客 ID：

| visit_id | customer_id |
| --- | --- |
| 1 | 10 |
| 2 | 20 |
| 3 | 20 |
| 4 | 30 |
| 5 | 40 |
| 6 | 40 |
| 7 | 40 |

你可以发现，顾客 ID 会重复，因为一个顾客可以到店多次；到店记录的 ID 不能重复，否则就分不清是哪一次了。

这里我们把 `visit_id` 定义为**主键**，用来区分每行数据。主键不能重复，也不能是 NULL。图中的编号是递增的，但主键并不要求必须自增，也可以使用 UUID 等其他编号。

UUID 和自增 ID 都可以作为主键，但长度和有序程度不同，会影响存储和查找。第三节介绍索引结构时，再来看它们的区别。

索引可以先理解成目录：没有对应的目录，就可能需要挨个检查记录；有了目录，就能先缩小查找范围。

不过，不能说 InnoDB 的表“默认没有索引”。定义主键时，就有了主键索引；没有主键，InnoDB 会使用第一个所有列都非空的唯一索引，再没有就生成隐藏行 ID 来组织数据。它不会任意挑一个普通列，替你建立查询索引。[聚簇索引选择规则](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html)

第二张表叫 `Transactions`，每行是一笔交易。`transaction_id` 是唯一且非空的交易编号，`visit_id` 对应到店记录，`amount` 是金额：

| transaction_id | visit_id | amount |
| --- | --- | --- |
| 101 | 1 | 50 |

两张表都有 `visit_id`，这次就可以按它把到店记录和交易关联起来。

这里要注意，同名列不一定有关联，是它们代表的含义决定了能不能这样连接。如果声明外键约束，可以让 `Transactions.visit_id` 引用 `Visits.visit_id`，方向不能反过来说。**写 JOIN 不要求事先声明外键**，连接条件由 SQL 里的 `ON` 指定。

## SQL 与输出

我们假设要做的是：**找出没有交易的到店记录，统计每个顾客有几次；只保留至少两次的顾客，按次数从多到少排列，最后取第一名。** 次数相同，就按顾客 ID 从小到大排。

“至少两次、排序、取第一名”是为了说明语法加的条件，不是原题要求。

```sql
SELECT v.customer_id, COUNT(*) AS count_no_trans -- 6. 展示顾客 ID、未交易次数
FROM Visits AS v                                 -- 1. 取到店记录，别名 v
LEFT JOIN Transactions AS t                      -- 2. 保留左表，连接交易表 t
  ON t.visit_id = v.visit_id                     -- 2. 匹配 visit_id，未匹配补 NULL
WHERE t.transaction_id IS NULL                   -- 3. 筛选没有交易的到店记录
GROUP BY v.customer_id                           -- 4. 按顾客分组，统计每组行数
HAVING COUNT(*) >= 2                             -- 5. 只留次数至少为 2 的组
ORDER BY count_no_trans DESC, v.customer_id ASC  -- 7. 次数降序，顾客 ID 升序
LIMIT 1;                                         -- 8. 取第一行
```

下面把几个关键步骤展开。它们是帮助理解的**逻辑结果示意**，不表示 MySQL 一定逐步生成这些中间表；没有 `ORDER BY` 时，行的顺序也没有保证。

**第 2 步结束：两张表按 visit_id 连接。**

`LEFT JOIN` 保留左表的到店记录，右表匹配不上就补 NULL。注意这里有两个 `visit_id`：一个来自到店表，一个来自交易表。浅橙色的这一行有交易，下一步会被筛掉。

| v.visit_id | v.customer_id | t.transaction_id | t.visit_id | t.amount |
| --- | --- | --- | --- | --- |
| <mark data-table-row="exclude">1</mark> | 10 | 101 | 1 | 50 |
| 2 | 20 | NULL | NULL | NULL |
| 3 | 20 | NULL | NULL | NULL |
| 4 | 30 | NULL | NULL | NULL |
| 5 | 40 | NULL | NULL | NULL |
| 6 | 40 | NULL | NULL | NULL |
| 7 | 40 | NULL | NULL | NULL |

**第 3 步结束：WHERE 只保留交易编号为 NULL 的行。**

顾客 10 的那次到店有交易，被筛掉了。高亮的是 WHERE 判断用的交易编号：为 NULL 的才留下。

| v.visit_id | v.customer_id | t.transaction_id | t.visit_id | t.amount |
| --- | --- | --- | --- | --- |
| 2 | 20 | <mark>NULL</mark> | NULL | NULL |
| 3 | 20 | <mark>NULL</mark> | NULL | NULL |
| 4 | 30 | <mark>NULL</mark> | NULL | NULL |
| 5 | 40 | <mark>NULL</mark> | NULL | NULL |
| 6 | 40 | <mark>NULL</mark> | NULL | NULL |
| 7 | 40 | <mark>NULL</mark> | NULL | NULL |

**第 4 步结束：按 customer_id 分组，计算每组的行数。**

顾客 20 两次，顾客 30 一次，顾客 40 三次。这里用表格表示分组与计数，不再把每条到店记录都列出来。浅橙色的顾客 30 只有一次，下一步会被筛掉：

| customer_id | COUNT(*) |
| --- | --- |
| 20 | 2 |
| <mark data-table-row="exclude">30</mark> | 1 |
| 40 | 3 |

**第 5 步结束：HAVING 只保留次数至少为 2 的组。**

顾客 30 被筛掉了。`WHERE` 筛的是行，`HAVING` 在这里筛的是分组后的计数。浅蓝色标出次数最多的顾客 40，接下来会排在最前面。

| customer_id | COUNT(*) |
| --- | --- |
| 20 | 2 |
| <mark data-table-row="focus">40</mark> | 3 |

之后 `SELECT` 选出顾客 ID 和计数，把计数列命名为 `count_no_trans`；`ORDER BY` 按次数降序排，顾客 40 就在前面。

**第 8 步结束：LIMIT 1，只返回第一行。最终输出：**

| customer_id | count_no_trans |
| --- | --- |
| <mark data-table-row="focus">40</mark> | 3 |

如果改成 `LIMIT 2`，就会再返回一行 `20、2`。`DESC` 是降序，`ASC` 是升序。

**SELECT 写了什么列或表达式，结果就展示什么列。** 这条语句最后只展示两列，不会把前面连接时出现的所有列都带出来，也不会修改原表。

MySQL 允许 `ORDER BY`、`GROUP BY`、`HAVING` 引用 SELECT 别名，同层 WHERE 不能直接引用它。[别名规则](https://dev.mysql.com/doc/refman/8.4/en/problems-with-alias.html)

## 关于几个连接

笔记里的这张图，可以帮助记住连接时保留哪一侧的记录：

![INNER、LEFT、RIGHT、FULL JOIN 保留范围示意，MySQL 不直接支持 FULL JOIN](/images/mysql/05-join-venn.svg)

- `INNER JOIN`：只返回两侧满足连接条件的匹配行。
- `LEFT JOIN`：保留左表的全部行，右表没有匹配时，对应列补 NULL。
- `RIGHT JOIN`：保留右表的全部行，左表没有匹配时补 NULL。通常交换两表的位置，就能改写成 LEFT JOIN。
- `CROSS JOIN`：两表的行两两配对，也就是笛卡尔积。左表有 3 行、右表有 2 行，就得到 6 行。

图中还有 `FULL JOIN`，表示两侧的未匹配记录也都保留；MySQL 不直接支持 `FULL OUTER JOIN`，需要组合查询来模拟。

维恩图只帮助记“保留哪一侧”，并不是说 JOIN 会自动去重。如果一条到店记录匹配了两笔交易，连接结果里就会有两行。

本题要找的是“到店但没有交易”。如果直接 INNER JOIN，没有交易的到店记录在连接时就消失了，所以这里先用 LEFT JOIN 留住它们，再用 WHERE 筛选。

<details>
<summary>SELECT 查询的逻辑处理顺序是什么？</summary>

常见的逻辑顺序是：

`FROM / JOIN ... ON → WHERE → GROUP BY 与聚合 → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT / OFFSET`。

它描述结果的形成语义，SQL 的书写顺序仍然以 SELECT 开头；优化器可以做等价的连接重排、条件下推等变换，物理执行不必逐步照搬这个顺序。

本文代码的编号只计算该语句实际使用的子句，并把分组和聚合合并计为一步。MySQL 允许 `GROUP BY`、`HAVING`、`ORDER BY` 使用 SELECT 别名，同层 WHERE 不能直接使用这些别名。

</details>

<details>
<summary>WHERE 和 HAVING 有什么区别？</summary>

**WHERE 在分组聚合前筛选行，HAVING 在分组聚合后筛选组或聚合结果。**

- WHERE 决定哪些输入行参与后续计算，不能直接使用同层的聚合结果，例如 `COUNT(*) >= 2`。
- HAVING 可以使用 `COUNT()`、`SUM()` 等聚合值，例如筛选订单数至少为 2 的用户。
- HAVING 不要求一定写出 GROUP BY；不带 GROUP BY 的聚合查询，也可以对整体聚合结果进行筛选。

能在聚合前确定的行条件，应写清为 WHERE；依赖聚合值的条件放在 HAVING。

</details>

<details>
<summary>INNER JOIN 与 LEFT JOIN 有什么区别？ON 与 WHERE 呢？</summary>

- **INNER JOIN**：只返回满足连接条件的匹配行。
- **LEFT JOIN**：保留左表的行；没有右表匹配时，右表列补 NULL。
- **ON**：定义连接阶段的匹配条件。
- **WHERE**：继续筛选连接结果；在逻辑上也会检查外连接补出的 NULL 行。

因此，LEFT JOIN 中把右表条件从 ON 移到 WHERE，可能过滤掉未匹配的左表行。例如 `WHERE t.amount > 0` 不能让补出的 NULL 行通过；`WHERE t.transaction_id IS NULL` 则可用于保留未匹配行，前提是用于判断的右表列在真实匹配记录中不为 NULL。本文的 `transaction_id` 是唯一且非空的交易编号。

不是所有条件移动都会改变结果，必须结合连接类型和 NULL 语义判断。[JOIN 规则](https://dev.mysql.com/doc/refman/8.4/en/join.html)

</details>

<details>
<summary>COUNT(*)、COUNT(1)、COUNT(列) 有什么区别？</summary>

- `COUNT(*)` 统计查询结果中的行数，行中包含 NULL 也计数。
- `COUNT(1)` 统计常量 1 的非 NULL 个数，所以同样是在数行。InnoDB 对它与 `COUNT(*)` 采用相同处理，没有固定的性能优势。
- `COUNT(列)` 只统计该列不为 NULL 的行，因此结果可能小于前两者。

比如 `demo` 表只有下面这一列：

| value |
| --- |
| 10 |
| NULL |
| 20 |

```sql
SELECT
  COUNT(*) AS all_rows,      -- 2. 数行数，有 NULL 的行也算
  COUNT(1) AS constant_rows, -- 2. 每行的常量 1 都非 NULL，也是在数行
  COUNT(value) AS values_num -- 2. 只数 value 不为 NULL 的行
FROM demo;                  -- 1. 从 demo 表取数据
```

输出：

| all_rows | constant_rows | values_num |
| --- | --- | --- |
| 3 | 3 | 2 |

`COUNT(1)` 里的 1 是常量，不是“第一列”。`COUNT(value)` 才是在检查某一列。

本题过滤后 `t.transaction_id` 全是 NULL，所以 `COUNT(t.transaction_id)` 为 0，应使用 `COUNT(*)` 统计未交易的到店记录。

InnoDB 不维护对所有事务都通用的精确总行数；无条件 `COUNT(*)` 仍需要统计当前事务可见的索引记录，不能回答成固定的 O(1)。[COUNT 的定义与 InnoDB 行数统计](https://dev.mysql.com/doc/refman/8.4/en/aggregate-functions.html)

</details>

</div>

# 三、InnoDB 怎样通过索引找到记录

第一节提到，存储引擎负责数据的具体组织与访问。本文用的 InnoDB，也是 MySQL 8.4 的默认存储引擎。

先把它和另一个常见引擎 MyISAM 作个比较，事务和锁的内容在第三篇再展开：

| 能力 | InnoDB | MyISAM |
| --- | --- | --- |
| 事务提交与回滚 | 支持 | 不支持 |
| 写入时的锁粒度 | 支持行级锁，也有表级锁 | 主要是表级锁 |
| 外键约束 | 支持 | 不支持 |
| 表数据组织 | 由聚簇索引组织 | 数据与索引文件分离 |

<div class="interview-group">

**面试串联**

<details>
<summary>InnoDB 和 MyISAM 有什么区别？为什么通常使用 InnoDB？</summary>

可以从事务与可靠性、并发能力、存储组织三个方面回答：

1. **事务与可靠性**：InnoDB 支持事务提交、回滚和崩溃恢复，也支持外键；MyISAM 不支持事务和外键，不能提供同等的事务崩溃恢复能力。
2. **并发能力**：InnoDB 支持行级锁和 MVCC；MyISAM 主要使用表级锁，不支持 MVCC。InnoDB 也有表级锁，不能把它描述成“只有行锁”。
3. **存储组织**：InnoDB 用聚簇索引组织行数据，二级索引携带聚簇键；MyISAM 的数据文件与索引文件分离，索引记录引用数据记录的位置。

InnoDB 是 MySQL 8.4 的默认引擎，通常更适合需要并发写入和可靠性的通用业务，不能笼统地说“MyISAM 查询总是更快”。[InnoDB 能力](https://dev.mysql.com/doc/refman/8.4/en/innodb-introduction.html) · [MyISAM 能力](https://dev.mysql.com/doc/refman/8.4/en/myisam-storage-engine.html)

</details>

## 先看表，再看树

回到第一节的 `orders` 表。`id` 是订单主键，`user_id` 是用户编号，`amount` 是金额，`status` 是支付状态：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 1 | 1 | 120.00 | paid |
| 2 | 1 | 80.00 | paid |
| 3 | 2 | 160.00 | paid |
| 4 | 2 | 90.00 | paid |
| 5 | 3 | 60.00 | paid |
| 6 | 3 | 70.00 | paid |
| 7 | 4 | 300.00 | paid |
| 8 | 3 | 900.00 | unpaid |

InnoDB 把记录放在一个个**页**里。一个页里有多行数据，还要放页头、页目录这些管理信息。普通索引页默认是 **16 KiB，也就是 16384 字节**，一页能放多少行，要看记录有多大。[InnoDB 索引的物理结构](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

页少的时候还好理解，页多了，怎么知道该找哪一页？可以在上面再放一层目录，记录键值和对应的子页；这一层放不下，就再加一层。先看图：

![三级主键 B+ 树：根页和中间页导航，叶子页 A 展开订单 1～8，叶子页之间双向连接](/images/mysql/01-storage-tree-overview.svg)

从上往下，整棵树是 **根页 → 中间页 → 叶子页**。根和中间页里的黄色格是导航键，白色格指向下一层的页；叶子页里的黄色格是主键，绿色格是这行的其他数据。

我们平时见到的二叉树，一个节点最多有两个子节点。但这里一个页可以指向很多子页，所以叫**多路**；叶子页都在同一层，所以树是平衡的。这就是后面一直会提到的 **B+ 树**。

注意，一个节点就是一个页，不是一行记录。图中叶子页 A 放着前面这 8 条订单，B、C 和上方其他分支省略了内容。为了说明大表结构，图里画了三层；如果表里真的只有这 8 条短记录，通常一页就能放下，根页本身也就是叶子页。

我们给这张表定义了 `PRIMARY KEY (id)`，因此这棵按主键组织行数据的树，就是它的**聚簇索引**。主键索引不是只存一个编号，找到叶子记录后，就能取得这行的数据。很长的字段可能用页外存储，这里先按图里的短记录理解。[InnoDB 行格式](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html)

## 知道 ID，怎样找到那一行

现在查第一节的 `WHERE id = 6`。

先看根页，图里用 1、25、49 表示三个分支的下界。6 小于 25，进入左侧中间页；这个中间页用 1、9、17 指路，6 小于 9，就进入叶子页 A。

这样，其他分支都不用找了。到了 A 页，再从页内找到编号为 6 的记录，返回：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 6 | 3 | 70.00 | paid |

是不是有点像二分查找？共同点是，**利用有序关系，排除不可能的范围**。不过 B+ 树一个节点有很多分支，并不是每次只分成左右两半；页内部具体怎样查，第四节再看。

图里的下界是为了方便看懂导航。实际 InnoDB 的最左项有特殊最小标记，父层的导航键也不保证始终等于子页当前最小值。记住“按键值选择子页”就可以了。

## 为什么用 B+ 树，三层能放多少行

这里最直接的好处，就是**分支多，树不用长得很高**。

比如假设一个内部页能指向 1000 个子页，一个叶子页能放 100 条记录：

| 树高，包含根和叶子 | 计算 | 大致容量 |
| --- | --- | --- |
| 1 层，根就是叶子 | 100 | 100 条 |
| 2 层，根 → 叶子 | 1000 × 100 | 10 万条 |
| 3 层，根 → 中间页 → 叶子 | 1000 × 1000 × 100 | 1 亿条 |

加一层，就能多覆盖很多页。不过这几个数都是假设，不是说 MySQL 的三层树固定存一亿行。主键越长、行越大，一页能放的内容就越少，还得扣掉页头、页目录等空间。

再看其他结构：二叉树的分支少，数据多时通常需要更多层；B 树的内部节点也存用户记录，会占用导航项的空间；普通哈希结构擅长等值查找，但不能像有序树这样沿着键值顺序做范围扫描。[B-tree 与 Hash 索引](https://dev.mysql.com/doc/refman/8.4/en/index-btree-hash.html)

**面试串联**

<details>
<summary>为什么 InnoDB 普通索引选择 B+ 树，而不是 B 树、二叉树或哈希表？</summary>

B+ 树是一棵**多路、平衡、有序**的搜索树，适合按页访问数据：

- **相比二叉树**：一页可以保存多个导航项，分支数大，通常能用更少层数覆盖更多记录。
- **相比 B 树**：非叶子页主要保存导航键和子页引用，数据记录集中在同一层叶子页；在相似页大小和键大小下，内部页更容易容纳较多导航项。
- **相比哈希表**：保持键值顺序，适合范围查找和有序扫描；哈希结构主要适合完整键等值定位。
- **范围查询**：先定位范围起点，再沿叶子页链接继续扫描，不必逐条从根查找。

选择依据是页式存储与多种查询方式的综合成本，不代表 B+ 树在所有内存等值查询中都比哈希快。这里讨论普通有序索引，全文和空间索引另有结构。

</details>

<details>
<summary>三层 B+ 树能存多少条记录？怎样估算？</summary>

没有固定答案。应先给出页大小、键与子页引用大小、记录大小，以及页利用率的假设。

设每个内部页平均有 `f` 个分支，每个叶子页平均放 `L` 条记录，树高 `h` 包含根和叶子。在分支数近似均匀的教学模型中，容量约为 `f^(h-1) × L`。

例如本文假设 `f = 1000`、`L = 100`，三层约为 `1000 × 1000 × 100 = 1 亿` 条。真实估算需要扣除页头、记录头和页目录等开销，并考虑页利用率。这个容量估算也不能推导出固定的磁盘 I/O 次数。

</details>

## 范围查询怎样继续往后读

如果想取得编号 5～7 的订单：

```sql
SELECT id, amount       -- 3. 最终展示编号、金额两列
FROM orders             -- 1. 从订单表取数据
WHERE id BETWEEN 5 AND 7 -- 2. 保留编号 5～7，包含两端
ORDER BY id;            -- 4. 按编号升序排列
```

输出：

| id | amount |
| --- | --- |
| 5 | 60.00 |
| 6 | 70.00 |
| 7 | 300.00 |

先找到 5，再往后读 6、7，不需要每条记录都从根重新找一遍。这个例子里的记录都在 A 页。如果范围跨到下一页，就沿叶子页之间的链接继续读。

所以图里的叶子页除了从上往下的连线，彼此之间还有**双向链接**。这里的相邻是索引顺序上的相邻，不保证它们在磁盘上紧挨着。[InnoDB 页链接实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/btr/btr0btr.cc)

## 按其他列查，为什么还要建索引

前面知道的是订单 ID。如果现在只有用户 ID，想查用户 3 的全部订单呢？

看订单表，这几条记录的主键是 5、6、8，中间的 7 属于另一个用户。主键树按订单 ID 排，不是按用户排，所以不能拿 `user_id = 3` 直接沿刚才的主键范围找。

这时可以给 `user_id` 再建一棵索引：

```sql
CREATE INDEX idx_user_id ON orders (user_id); -- 给 user_id 建立二级索引，不改变原表的列
```

这棵树叫**二级索引**，也叫辅助索引。它按 `user_id` 排列，叶子记录存的是 `user_id` 和对应的主键 `id`，可以简化成：

| user_id | 订单主键 id |
| --- | --- |
| 1 | 1 |
| 1 | 2 |
| 2 | 3 |
| 2 | 4 |
| 3 | 5 |
| 3 | 6 |
| 3 | 8 |
| 4 | 7 |

你可以发现，同一个用户的索引项，现在排到一起了。但它没有保存金额、支付状态等所有字段。

## 回表：拿到主键，再查一次

```sql
SELECT id, user_id, amount, status -- 3. 最终展示这四列
FROM orders                       -- 1. 从订单表取数据
WHERE user_id = 3                  -- 2. 只保留用户 3 的订单
ORDER BY id;                      -- 4. 按订单编号升序排列
```

假设优化器选择使用 `idx_user_id`，查询就可以分成两段：先在二级索引里找到主键 5、6、8，再拿这些主键去聚簇索引取金额、支付状态。

![user_id 索引找到主键 5、6、8，展开 id 为 6 时访问主键树、取得金额和状态的过程](/images/mysql/04-secondary-lookup.svg)

**从二级索引取得主键，再去聚簇索引取记录，这个过程就是回表。** 二级索引保存的是主键值，不是这行的磁盘地址。

输出：

| id | user_id | amount | status |
| --- | --- | --- | --- |
| 5 | 3 | 60.00 | paid |
| 6 | 3 | 70.00 | paid |
| 8 | 3 | 900.00 | unpaid |

这里没有筛选支付状态，所以未支付的订单 8 也在结果里。图中只展开了订单 6 的一次回表，另外两条也需要取得查询要求的列。

## 覆盖索引：需要的列，索引里已经有了

如果我只要用户 ID 和订单 ID，把 SELECT 改一下：

```sql
SELECT user_id, id -- 3. 最终只展示用户编号、订单编号
FROM orders        -- 1. 从订单表取数据
WHERE user_id = 3   -- 2. 只保留用户 3 的订单
ORDER BY id;       -- 4. 按订单编号升序排列
```

输出：

| user_id | id |
| --- | --- |
| 3 | 5 |
| 3 | 6 |
| 3 | 8 |

这两列在 `idx_user_id` 里都有，不需要为了取金额、状态再查主键树了。这就叫**覆盖索引**：查询需要的列，已经被当前使用的索引包含。

所以它不是一种单独的建索引语法。同一棵索引，换一下 SELECT 的列，就可能从覆盖变成需要回表。

有索引，也不意味着优化器一定使用它。比如表里真的只有 8 条记录，直接扫描可能也很便宜。第二篇再用 EXPLAIN 看实际选择；这里先把两种查法分清。

<details>
<summary>InnoDB 聚簇索引和二级索引有什么区别？</summary>

区别在于**叶子记录保存什么，以及表数据怎样组织**：

- 聚簇索引的叶子记录承载行数据；一张 InnoDB 表只有一个聚簇索引，因为行数据只能按这一套聚簇键顺序组织。
- 二级索引的叶子记录保存二级索引列值和对应的聚簇键；一张表可以有多个二级索引。本文显式声明了主键，因此聚簇键就是主键。
- 二级索引保存的是键值，不是行的固定磁盘地址。需要它未包含的列时，再按聚簇键访问聚簇索引。

很长的变长字段可能使用页外存储，“叶子记录承载行数据”不意味着一行所有字节必定在同一页。

</details>

<details>
<summary>什么是回表和覆盖索引？覆盖索引一定完全不访问聚簇记录吗？</summary>

**回表**：通过二级索引取得聚簇键，再访问聚簇索引取得所需记录。

**覆盖索引**：某条查询所需的过滤、连接和返回列等，已经包含在使用的索引中，可以从该索引取得结果，省去为获取额外列而回表。覆盖与否是索引和具体查询之间的关系，不是一种独立的建索引语法；修改 SELECT 的列可能改变覆盖情况。

**边界**：字段被覆盖，不代表任何情况下都完全不访问聚簇记录。InnoDB 在二级索引记录带有删除标记，或需要检查较新修改的可见性等情况下，仍可能访问聚簇记录。这里的“避免回表”主要解释获取列的路径，多版本可见性会在第三篇展开。[InnoDB 多版本与覆盖索引](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

</details>

## 索引也要维护，再来看自增 ID 和 UUID

索引不是建完就不管了。插入一行，聚簇索引和相关二级索引都要加记录；修改索引列、删除数据，也要维护对应的索引。索引越多，要占的空间和写入工作通常也越多。

新记录应该插在哪里，由键值决定。目标页还有空间，就可以放进去；空间不足时，可能先整理，必要时再分配新页、分开记录、修改父层导航项，这就是**页分裂**。父页也放不下时，还可能继续向上调整。

再回到第二节的问题：为什么主键用自增整数很常见？

第一，整数通常比较短。二级索引也要带上主键，主键越长，每棵二级索引占的空间也会变大。

第二，自增值通常靠近已有主键的末尾，新记录的插入位置比较集中。随机 UUID 的新值可能落在不同范围，就可能需要访问不同的页，目标页满了还会分裂。如果再用很长的字符串存 UUID，空间开销也会更大。

所以在不需要分布式生成 ID 等额外条件时，自增整数是常见选择。需要 UUID 时，要一起考虑生成方式、编码长度和有序程度；紧凑存储的有序 UUID，不能和随机长字符串一概而论。

自增也不是永远没有页分裂，页满了仍要分配新页，高并发下还可能有尾页热点。[主键长度的影响](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) · [顺序与随机插入](https://dev.mysql.com/doc/refman/8.4/en/innodb-physical-structure.html)

<details>
<summary>什么是索引？索引有哪些收益和代价？</summary>

**索引是帮助存储引擎快速定位记录的数据结构，用额外空间和写入维护换取更少的扫描。**

- **收益**：加快合适的等值、范围查询；利用有序性减少部分排序；通过唯一索引约束唯一性，通过覆盖索引减少额外取列的回表。
- **代价**：占用磁盘和 Buffer Pool 空间；插入、删除、更新相关列时需要维护索引，索引越多通常意味着更多写入工作。
- **适用条件**：是否受益取决于查询条件、数据分布、返回行数和回表成本。有索引不等于优化器一定选择它，不能笼统地说“加索引一定更快”。

</details>

<details>
<summary>插入、更新、删除数据时，索引会发生什么变化？</summary>

- **插入**：需要向聚簇索引和相关二级索引加入记录。页有空间时可以直接插入；空间不足时可能重组或分裂，并更新页链接和父层导航项。
- **更新**：索引列的键值变化时，需要维护旧索引项和新索引项；修改聚簇键还会影响相关二级索引。只更新非索引列，不需要重新排列该二级索引，但行长度变化仍可能影响聚簇记录的页内布局。
- **删除**：InnoDB 通常先做删除标记，满足清理条件后再由后台 purge 清理；不是执行 DELETE 后所有索引页立即收缩。页利用率降低后也可能发生页合并或重组。

不是每次插入都会分裂，也不是每次分裂都会增加树高；需要根部增层时，树高才会增加。[InnoDB 多版本与索引维护](https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html)

</details>

<details>
<summary>主键应该使用自增 ID 还是 UUID？</summary>

InnoDB 的主键会组织聚簇索引，并进入相关二级索引，因此通常希望它**短、稳定、唯一，并尽量保持有序**。

- **自增整数**：键值紧凑、比较简单，新记录通常靠近主键树尾部，可减少分散的随机页访问；但仍会分配新页，高并发下也可能出现尾页热点。
- **随机 UUID**：插入位置更分散；若使用较长字符串编码，还会放大聚簇索引和二级索引的体积。
- **选择条件**：需要全局唯一 ID 时，还要比较生成方式、编码长度、有序程度和业务约束；紧凑编码、近似有序的 ID 与随机长字符串不能一概而论。

不能回答成“自增永远更好”或“UUID 必然不能用”。主键变长影响所有携带它的二级索引，近似递增则主要影响记录插入位置。

</details>

## Buffer Pool：页可能已经在内存里

看到这里，你可能会算：三层树，找一条记录是不是要读三次磁盘？

不一定。InnoDB 会把数据页、索引页缓存在内存的 **Buffer Pool（缓冲池）** 中。要访问的页已经在里面，就直接读内存；不在，才需要把页读进来。[Buffer Pool](https://dev.mysql.com/doc/refman/8.4/en/innodb-buffer-pool.html)

![Buffer Pool 位于 MySQL 进程内：已缓存的根页、中间页和 A 页可以直接读内存；未缓存的 B 页需要先从磁盘整页读入](/images/mysql/06-buffer-pool.svg)

图里假设根页、中间页、A 页都已经缓存了。按前面的主键树查 `id = 6`，访问的这几个页都能在内存中找到，就不需要为了这次查找重新读磁盘。

如果之后需要访问 B 页，而它还没缓存，就先把 B 页读入 Buffer Pool，再在内存里查找记录。读入的是一整个页，不是只把某一行拎出来。图里的虚线框表示 B 页读入后的示意位置，不是已经缓存的页。

这也就和第一节的旧查询缓存区分开了：**查询缓存存 SQL 的结果，Buffer Pool 缓存页**。即使两条 SQL 不同，也可能用到同一个页。

树高告诉我们从根到叶子经过几层页，不能直接当成实际磁盘读取次数。

# 四、找到页以后，怎样找到那条记录

前面说，沿主键树进入 A 页，然后找到编号为 6 的记录。现在把 A 页放大，看看这最后一步。

## 每条记录，还有一个记录头

我们往表里存的是 `id、user_id、amount、status` 这些字段。但 InnoDB 要管理这些记录，还需要额外保存一些信息，比如下一条记录在哪里。

所以，一条记录可以先拆成两部分看：

```text
记录 6 = 记录头里的管理信息 + 业务数据（id=6、amount=70.00 等）
```

**记录头属于每条记录，页头属于整个页**，这两个别混了。记录头里有一个 `next`，用来找到下一条记录。比如订单 6 的 next 指向订单 7，订单 7 的 next 再指向订单 8。

你可以把 next 当成链表的指针理解。不过这里保存的是相对位置，不是把下一条的主键值 7 直接存进去。这样，同一页里的记录就能按主键顺序串起来，即使它们在页内的实际存放位置并不挨着。

## infimum：可以类比链表里的哑节点

如果你写过链表，可能用过**哑节点（dummy node）**：它不放业务数据，放在链表最前面，方便找到第一条真正的数据。

InnoDB 的索引页里也有一个类似的头部节点，叫 **infimum**。准确地说，它是表示页内最小边界的系统记录，可以把它理解成链表的头部哑节点。

注意，它不等于“ID 最小的那条订单”。图里最小的订单是 1，就算删掉订单 1，infimum 也还在；之后再插入更小的 ID，也仍然排在它后面。

链尾还有一个 **supremum**，作为最大边界的哨兵。它们由 InnoDB 自动维护，不需要我们 INSERT，也不会作为订单出现在 SELECT 结果中。

![一条订单由记录头和业务数据组成；A 页的记录从头部哑节点 infimum 单向连接到尾部哨兵 supremum，空页时也保留这两个系统记录](/images/mysql/02-record-chain.svg)

所以，把 A 页的记录链完整画出来，就是：

```text
infimum → 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8 → supremum
```

即使页里还没有订单，也是 `infimum → supremum`。从 infimum 的 next 开始，就能找到第一条用户记录；如果直接到了 supremum，就说明这一页没有用户记录。[系统记录的源码定义](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/include/page0page.h)

## 记录多了，分成几组

记录可以沿链从头往后找，但页里的记录多了，查找靠后的 ID 就要经过更多记录。页目录可以先缩小查找范围。InnoDB 没有给每条记录都放一个目录项，而是先把记录分成几小组，每组选最后一条记录作为代表。

比如 A 页的这 8 条订单，我们假设这样分：

```text
第一组：1 → 2 → 3 → 4，组末是 4
第二组：5 → 6 → 7 → 8，组末是 8
```

这就是这里说的“分组”。它是 InnoDB 为了管理和查找记录维护的分组，和 SQL 的 `GROUP BY` 没关系；原来的 next 仍然把这些记录连成一整条链。

那么怎么知道一组有几条？再看记录头里的另一个字段 **`n_owned`**，表示这条记录负责多少条记录：

- 记录 4 的 `n_owned = 4`，负责 1、2、3、4，包含自己。
- 记录 8 的 `n_owned = 4`，负责 5、6、7、8，同样包含自己。
- 其余普通记录的 `n_owned = 0`，意思是它不是组末记录，不负责一个组；不是说它没有数据。

普通组通常有 4～8 条记录，首尾组允许例外。这里分成两组各 4 条，是为了方便看图；实际插入同样的数据，不保证得到同样的分组。[分组数量的源码定义](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/include/page0page.h)

## 目录槽，就是目录里的一项

**页目录（Page Directory）** 里的每一项，叫作一个**目录槽（slot）**，你可以先把它理解成一个小格子，里面保存组末记录的位置。

在这张图里，目录是这样的：

```text
槽 0 → infimum
槽 1 → 记录 4
槽 2 → 记录 8
槽 3 → supremum
```

这里要分清：**槽里存的是记录在页内的位置，不是直接存主键 4 或 8，也不是把整组记录塞进槽里。** 通过这个位置找到记录以后，才能读到它的主键。

![A 页的完整结构：记录头中的 n_owned、next 与业务字段分开标注；目录槽指向头部哑节点 infimum、组末记录 4、8 和尾部哨兵 supremum](/images/mysql/02-page-directory.svg)

图里，infimum 和 supremum 也各自一组，所以四个槽指向的记录，计数分别是：

| 槽指向的记录 | 记录头里的 n_owned | 负责哪些记录 |
| --- | --- | --- |
| infimum | 1 | 本图中只有自己 |
| 记录 4 | 4 | 1、2、3、4 |
| 记录 8 | 4 | 5、6、7、8 |
| supremum | 1 | 本图中只有自己 |

红色虚线表示目录槽指向记录，黑线表示 next 指向下一条记录。图按逻辑顺序排布，不表示页内的真实字节位置。

## 再查一次 id = 6

有了目录，找 6 就不用从第一条订单开始了：

![先对页目录的槽二分查找，通过所指记录确定 4 与 8 之间的分组，再从记录 4 沿单向链找到 5、6；槽中实际保存位置](/images/mysql/02-page-search.svg)

1. 先对目录槽做二分查找，通过槽指向的记录比较主键，确定 `4 < 6 <= 8`。
2. 这就知道了，6 在第二组。从**前一组末尾的 4** 开始，沿 next 找 5、6。
3. 找到 6，取出需要的业务字段。

为什么从 4 开始，不从 8 往回找？因为页内记录链是单向的，只能沿 next 往后走。目录里的 4 和 8，帮我们圈定了范围。

如果找的是 2 呢？它在第一组，从 `infimum → 1 → 2` 就能找到。这样，第一组也有一个固定的查找起点，就是前面说的头部哑节点。

这里用到的二分查找，查的是**目录里的槽**。槽的大小固定、排列紧凑，可以按下标访问；先通过它缩小范围，再沿记录链走几步。[页内查找实现](https://github.com/mysql/mysql-server/blob/mysql-8.4.0/storage/innobase/page/page0cur.cc)

另外，上一节说的是**叶子页与叶子页之间双向连接**，这里说的是**同一页里的记录单向连接**，这两个也别混了。

**面试串联**

<details>
<summary>定位到 B+ 树叶子页后，InnoDB 如何查找具体记录？</summary>

**通过页目录缩小范围，再沿页内记录链完成查找。**

1. 页内记录按索引键的逻辑顺序连接，并被划分为若干组；页目录中的槽指向各组的末尾记录。
2. 对目录槽做二分查找，通过槽指向的记录比较键值，确定目标所在的组。
3. 从前一组的末尾记录向后，沿记录链做少量比较，找到目标记录，或确认记录不存在。

页目录没有为每条记录建立一个槽；也不是找到组末后再倒着遍历。`n_owned` 是组末记录负责的记录数，其他普通记录的 0 不表示没有数据。内部索引页也使用页目录。

回头看第一节那条 `WHERE id = 6`，过程就连起来了：

```text
后端发送 SQL
  → Server 解析、优化，选择访问方式
  → 执行器调用 InnoDB
  → 沿主键 B+ 树找到 A 页，页可能已在 Buffer Pool 中
  → 通过页目录和记录链找到订单 6
  → 返回 SELECT 要求的列
```

按 `user_id` 查且使用二级索引时，可能多一步拿主键回表。第二节那样的连接、分组查询，还需要执行器按计划完成匹配和聚合，不能把所有 SQL 都理解成一次主键查找。
