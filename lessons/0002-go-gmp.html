Go 的 goroutine
由谁放到线程上执行？

本课目标：解释一次网络等待时 G、M、P 的关系，并判断 GOMAXPROCS 限制的是什么。

1. 从熟悉的 Node.js 出发

Node.js 常让一个 JS 主线程在异步网络等待期间处理其他回调。Go 也能在等待网络时推进其他任务，但开发者通常通过 go 创建 goroutine；Go runtime 把可运行的 goroutine 安排到操作系统线程上。

go callTool("A")   // 发起任务 A
go callTool("B")   // 发起任务 B

G1 ─┐
    ├── Go runtime 调度 ──→ M（操作系统线程）
G2 ─┘                        ↑
                    执行 Go 代码需要 P

这是简化示意：G 是 goroutine，M 是操作系统线程，P 是执行用户 Go 代码所需的调度资源。P 不是 CPU 物理核心，也不是线程池。它们的安排由 Go runtime 动态管理。[Go runtime 官方说明]

2. 一个任务等网络，另一个能做什么？

假设 G1 和 G2 都向外部服务发送请求，网络 I/O 由 Go runtime 的网络轮询机制管理。一种可能的时序：

① G1 在 M1 + P1 上运行，发起网络请求
② G1 等待网络，暂时不可运行
③ M1 + P1 可以运行 G2
④ G1 的网络事件就绪，G1 再次进入可运行状态
⑤ runtime 之后安排 G1 继续，未必还是 M1

等待期间，G1 保留后续执行需要的状态，但不必让一条线程一直等待这次网络响应。这不适用于所有阻塞：例如线程进入某些阻塞系统调用时，M 可能被阻塞，runtime 可以把 P 交给其他 M。[调度与系统调用]

3. GOMAXPROCS 管什么？

GOMAXPROCS 决定 P 的数量，限制同时执行用户 Go 代码的操作系统线程数量；它不是 goroutine 数量上限，也不是进程中线程总数上限。默认值受 Go 版本和环境影响。[官方 API]

写业务通常不手动为每个任务创建线程。你仍需要控制业务并发数：例如给下游工具调用设置上限、超时与取消，并检查共享数据的并发访问。
